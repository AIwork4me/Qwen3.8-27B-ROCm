# Qwen3.8-27B-ROCm — Design Spec

Date: 2026-08-16
Status: Approved in brainstorming (pending spec review)
Method: **Adapt → Validate → Benchmark → Explain → Reproduce**
Predecessor: Muse-Glimmer-30B-ROCm (`~/Desktop/muse-rocm`) — skeleton, evidence
patterns and installer are reused; content is rewritten for this model.

## 1. Goal

Deliver a top-quality open-source project that lets users run
**Qwen/Qwen3.8-27B** locally on **AMD ROCm 7.14.0**, with:

- **One-Pass Success** quickstart — defaults never lead users into an
  unvalidated or pathological configuration.
- **Measured, not guessed** performance and context-capacity evidence on the
  validated platform (Strix Halo / Radeon 8060S, `gfx1151`).
- **UX-first verdicts** — every benchmark configuration is graded
  ✅ Recommended / ⚠️ Caution / ❌ Avoid, and pits are documented so users can
  route around them in 30 seconds.
- A community **hardware-validation protocol** so additional platforms
  (notably W7900, `gfx1100`) can be added as comparable evidence.

## 2. Verified facts (input constraints)

Model (from ModelScope API, 2026-08-16):

- Architecture `Qwen3_5ForConditionalGeneration` (`model_type: qwen3_5`),
  multimodal (image + video vision tower), 248,320 vocab, 262,144 max
  position embeddings, MTP (`mtp_num_hidden_layers: 1`).
- 64 layers: 48 linear attention (GDN-style gated delta net, constant-size
  state) + 16 full attention (`full_attention_interval: 4`), GQA with
  `num_key_value_heads: 4`, `head_dim: 256`.
- BF16 weights ≈ 51.7 GiB (18 safetensors; sum of the published file sizes,
  recorded per file in `configs/artifact-manifest.json`).
  Requires transformers 5.8.0.dev0. ModelScope backend registry lists no vLLM/SGLang/Ollama/LMDeploy
  support yet → upstream support status must be established by spike.

Hardware/software:

- Validated host: AMD Ryzen AI MAX+ PRO 395 / Radeon 8060S, `gfx1151`
  (RDNA 3.5), 94 GiB system RAM with an 80 GiB GPU-visible unified-memory
  pool (rocminfo gfx1151 agent coarse-grained GLOBAL segment, measured
  2026-08-16; 32 GiB-class pools describe the minimum-SKU envelope, not
  this host). Kernel 6.17
  (≥ 6.16.9 per muse-rocm finding). System ROCm is currently 7.2.1; target
  stack is **ROCm 7.14.0** via the muse-rocm installer pattern.
  *Erratum 2026-08-16: this bullet originally read "32 GiB-class unified
  memory visible to ROCm" — the spec text understated the measured pool
  (the validated host's GPU-visible pool is 80 GiB; 32 GiB-class applies
  to minimum-SKU platforms such as R9700/32 GB). Feasibility conclusions
  derived from the 32 GiB premise were corrected in the spike receipts —
  see the erratum in `docs/results/spike/quant-kv.md` and
  `gpu_visible_pool_gib` in `configs/validated-stack.json`.*
- **W7900 is not present on this host.** It stays 🚧 Planned in the hardware
  matrix, gated on a protocol-compliant community submission.
- BF16 (51.7 GiB published shard sum — see `configs/artifact-manifest.json`)
  fits the measured 80 GiB GPU-visible unified-memory pool → quantization
  is a performance/efficiency choice, not a capacity requirement, on the
  validated host; it remains mandatory on 32 GiB-class SKU envelopes.

## 3. Approaches considered

- **A (chosen): Spike first, then dual-path with evidence-tiered emphasis.**
  A short reconnaissance establishes what actually supports `qwen3_5` today;
  each path is then either fully validated or its gap is recorded as a
  documented finding with upstream tracking.
- **B: Full dual-path without spike** — rejected: risk of mid-project walls
  and rework if upstream support is missing.
- **C: vLLM-only** — rejected by user decision (dual-path selected).

## 4. Architecture of the deliverable

### 4.1 Repository layout

Reuse the muse-rocm shape (proven for this workflow):

```
scripts/           00-check-env.sh, install-rocm-7.14.sh (reused),
                   vllm path (01-build, 02-fetch, 03-serve), gguf quickstart,
                   benchmark suite (SSE-framing-safe client), verdict
                   generator, README-block generator
configs/           validated-stack.json, benchmark verdict JSONs,
                   rocm-7.14 validation manifests (+ JSON schemas in schemas/)
docs/              adaptation.md, getting-started.md, troubleshooting.md,
                   hardware-validation.md, results/ (benchmark.md,
                   METHODOLOGY.md, matrix dirs), superpowers/specs/
tests/             unit + CI-gate tests (incl. quickstart-vs-verdict assert)
.github/           Actions CI (CPU-safe checks: schema validation,
                   generated-block freshness, quickstart flag audit)
LICENSE (Apache-2.0), CITATION.cff, CONTRIBUTING.md, SECURITY.md
```

### 4.2 Spike (before any validation work)

Answer, with receipts (commit hashes / versions / links):

1. vLLM: does a nightly/release register `Qwen3_5ForConditionalGeneration`?
   MTP support? On ROCm with TheRock PyTorch on `gfx1151`?
2. GGUF: does llama.cpp support `qwen3_5` (linear attention + MTP + vision)?
   Do community/official GGUF quants of Qwen3.8-27B exist? Is conversion
   viable (convert script + quantize)?
3. Official quantizations: AWQ/GPTQ/FP8 variants on ModelScope/HF?
4. KV-cache quantization support (`fp8` KV) on `gfx1151` in vLLM and
   llama.cpp.

Spike output: a decision table deciding, per path, "full validation now" vs
"recorded gap + upstream issue link". Recorded gaps are first-class findings
(`docs/results/`), not failures to hide.

### 4.3 Validation and benchmark design

**Three-dimensional matrix:** `concurrency (1/4/8/16) × weight/KV/MTP variant
× context tier (32K/128K/256K/262K)` per serving path, subject to spike
outcomes (path coverage may be reduced; every dropped cell is recorded with
reason).

**Measured per cell:** aggregate throughput, per-stream TPOT, TTFT,
time-to-first-token under long prompts, memory (weights/KV/activation split),
stability (errors/aborts), and — for reachable long-context cells — a
functional long-context retrieval smoke test (guards against "runs but
attention degraded" false positives). Greedy-decoding byte-identical smoke
check for the arithmetic anchor.

**KV memory feasibility model (documented, then measured):** only the 16
full-attention layers grow KV with context (48 linear-attention layers are
constant-state). Methodology documents the closed-form estimate
(KV bytes = tokens × 2 × full-attn layers × kv_heads × head_dim × dtype
bytes × concurrency) alongside weights + activations + MTP overhead, to
compute per-configuration context ceilings; benchmarks confirm actual
`max_usable_context`. KV dtype (bf16 vs fp8) is an explicit matrix variable —
it is the decisive lever for whether 262K fits in 32 GiB unified memory.

**Context capacity as a first-class per-concurrency question:** every
concurrency tier explores whether 262K (or the nearest reachable tier) works.
Dual-path context limits are recorded separately: vLLM `max-model-len`
behavior vs llama.cpp `--ctx-size` mmap/GTT spill cliff (a known user trap →
"known good and known bad").

### 4.4 UX-first verdict system

- Every benchmark cell carries `verdict: recommended | caution | avoid` with
  `reason`, `conditions`, `workaround`, `upstream` link — enforced by JSON
  schema; missing verdict fails tests.
- Demotion rules are pre-declared in METHODOLOGY.md, e.g.: per-stream TPOT
  below the interactive threshold when concurrency rises (default threshold:
  10 tok/s per stream, i.e. ≤ 100 ms/token, fixed in METHODOLOGY.md before
  any measurement); throughput that does not scale (or regresses) with c;
  aborts/OOM/instability; pathological resource spikes (the muse-rocm DFlash
  + `-np 16` 5h16m lesson, encoded structurally).
- **Known good and known bad** is a generated README block fed by the verdict
  JSONs (same pattern as hardware-matrix), so prose can never drift from
  evidence.
- **Quickstart hard guarantee:** quickstart scripts hard-code only
  ✅-verdict flag combinations; a CI test parses quickstart invocations and
  asserts every referenced parameter combination is `recommended` in the
  verdict JSONs. A PR pointing defaults at a pit goes red.
- Concurrency sweeps are framed as user journeys (single-user interactive,
  light multi-user, batch) — aggregate tok/s that destroys single-stream UX
  is reported as ❌, never showcased as a headline.
- Every ❌ pit gets the standard documentation format in troubleshooting.md:
  symptom → reproduction conditions → root cause / diagnosis state →
  workaround → upstream tracking link.

### 4.5 Adaptation map (`docs/adaptation.md`)

MI-series / Day-0 upstream recipes → RDNA `gfx1151` deltas, classified by
durability: memory placement (UMA/GTT vs HBM), quantization support surface
(AWQ/GPTQ/FP8/KV-fp8 on RDNA), MTP/speculative-decoding behavior, vision path
(mmproj / preprocessor), long-context memory ceiling strategies. W7900
(`gfx1100`) is listed as evidence-gated Planned.

## 5. Phase order

1. Spike (4.2) → decision table.
2. Install ROCm 7.14.0 (reused installer), `00-check-env.sh` green.
3. vLLM path: build/fetch/serve + validation (text, MTP, vision, context).
4. GGUF path: quickstart + validation — or recorded-gap documentation.
5. Benchmark matrix (4.3) with verdicts; negative results preserved.
6. Explain: README (generated blocks), adaptation map, methodology,
   troubleshooting, hardware-validation protocol.
7. Reproduce: clean-environment one-pass rehearsal of quickstart + verify
   steps; fix everything that is not one-pass.
8. Publish: CI green, tags, CITATION, changelog.

## 6. Testing

- Unit tests for scripts/verdict-generator/schema conformance (CPU-only CI).
- CI gates: schema validation of all `configs/*.json`; generated-block
  freshness (regenerate → no diff); quickstart-flags-vs-verdict assertion.
- On-host: benchmark cells emit raw JSON + manifest (exact command, flags,
  hashes, timestamps) into `docs/results/`; no hand-edited numbers.

## 7. Out of scope for v0.1

- W7900 / other dGPU validation (evidence-gated community submissions).
- Training/fine-tuning; serving anything beyond the two inference paths.
- ROCm versions other than 7.14.0 (7.2.1 may be referenced as historical
  context only, not re-validated).
